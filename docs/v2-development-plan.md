# TuneX V2.0 — 统一转发与彻底原生化重构开发方案

> 状态：**V2.0 破坏性重构设计基线，待实施**。由 V1.1 升级；旧版内容作为需求与历史现状说明，不再作为兼容承诺。代码参考基线：`PaiMonCai/TuneX` `main` `9ea59ae4787475d58ab41918b09158ac10d4f11f`（方案编制时核对，实施前必须重新确认 HEAD）。
>
> **最高优先级决策**：允许破坏性 API、Schema、Agent 协议、目录及部署方式变更；不保留无价值兼容层。最终生产路径不包含 ForwardX 源码、二进制、协议适配或构建依赖。允许开发中短暂过渡，但不得把双运行时作为最终架构。**数据与安全不因允许破坏性开发而豁免**。
>
> **V2.0 协议决议（2026-10-11）**：采用自主设计的 **TuneX Secure Transport（TST）`tst/1`**，完整替换 ForwardX FXP 数据面；采用成熟 TLS 1.3 / mTLS 密码学实现，不发明密码算法、不复制或改写 ForwardX 协议实现。最终不保留 FXP 协议兼容路径。新增第 23–27 节优先于前文所有 FXP 过渡描述。
>
> **核心业务模型**：Forward 是用户业务主体；Node 是执行资源；Transport 是传输方式；Link 是 TuneX 自有、可复用的内部安全连接资源。

## 1. 背景与目标

### 当前实际问题

1. `/forwards` 已可从一个弹窗选择 Native 或 FXP，但 FXP 仍先提交 Link、再提交 Forward，用户必须理解 Link 名称和载体端口。
2. FXP 编辑、暂停、恢复、重试、删除由 `/links/:id/forwards` 管理；普通 Forward 走原生服务，在 `/forwards` 点击 FXP 动作仍跳转 `/links`。
3. FXP 创建要求 `node:manage`，使普通的转发创建权限与底层节点管理权限耦合。
4. 业务协议、转发路径、客户端 TLS/WS 前端、节点间加密载体的概念未完全分离，容易把普通 RELAY 误认为已加密。
5. Link 当前限定同一 Workspace 的固定两个自有节点；FXP 能力默认关闭，尚不能把候选支持矩阵直接当正式发布承诺。

### 统一业务交付结果（继承 V1 需求）

- **唯一用户入口**：普通用户在 `/forwards` 完成创建、列表、详情、编辑、暂停、恢复、重试、删除和诊断；不因 FXP 强制跳转 `/links`。
- **一次业务提交**：创建 FXP Forward 时，由服务端查找安全可复用的 Link；没有合适 Link 则自动创建并配置载体端口。用户只提交一份业务表单，系统内部允许异步部署，但不可让用户手动补交第二份表单。
- **统一业务契约**：不同转发方式共享 ID、名称、入口、目标、协议、流量限额、期望状态与运行状态；过渡期原生与 FXP 走各自安全写入路径；最终统一到 TuneX 自主运行时。
- **清晰的状态与错误**：明确展示“已接受、配置待应用、已部署、运行就绪、目标健康或未知、失败需处理”；请求结果不明时可查询原操作，不重复创建。
- **开发期破坏性迁移**：允许重建未发布的旧 API 与数据模型；保留业务语义，迁移或显式废弃旧数据，不承诺旧实验版本兼容。

### U 系列（统一业务）不包含的范围

U 系列不新增 FXP 多跳、多入口/多出口、WireGuard V2、GOST、新执行驱动；不强制实现带引用 Link 的在线改端点/换密钥；不修改计费模型或 Windows 支持策略。这些继续由后续 F5/F6/F7 工作包处理。**V2.0 以原生替换为必达目标；原有 F 系列实验计划仅作历史参考，不能阻碍新架构收敛。**

## 2. 统一领域模型

| 概念 | 对外含义 | 内部职责 |
| --- | --- | --- |
| `Forward` | 用户创建的一条业务转发 | 监听端口、目标、协议、限额、状态、归属及业务修订 |
| `Node` | 入口或出口服务器 | 真实执行、能力上报、资源容量 |
| `Path` | 流量经过的拓扑 | `direct` / `relay`，V1 加密路径仅固定双节点 |
| `Transport` | 节点间采用的传输 | `native_plain` / `fxp_v1` / 规划中的 `tunex_secure_v1`；与客户端 TLS/WS 前端分离 |
| `LinkResource` | 内部共享加密连接 | 端点、载体端口、密钥、版本、部署、租约及引用关系 |

现有 U 系列准入组合（新原生协议在 N 系列完成前不可用）：

| 用户选择 | Path | Transport | 说明 |
| --- | --- | --- | --- |
| 普通直连 | `direct` | `native_plain` | 入口直接拨目标 |
| 普通中继 | `relay` | `native_plain` | 节点间原生 hop **不保证加密** |
| 加密中继 | `relay` | `fxp_v1` | 固定入口和出口的 FXP 加密通道 |

`tcp` / `udp` / `both` 是业务协议维度；客户端 TLS、WS 与 hop 加密是不同维度。每种组合均由真实 Agent 能力、实验开关、Workspace 策略和运行支持矩阵决定，未验证组合禁止提交，**禁止 FXP 不可用时静默降级为明文**。

## 3. 前端设计（一个页面完成业务操作）

### `/forwards` 主界面

- 保留概览、搜索、分页、排序；新增两个独立筛选维度：**转发路径**（直连/中继）与**传输方式**（普通/FXP），不混用标签。
- 每行显示名称、协议、入口地址/端口、节点路径、目标、传输、期望/运行状态与最近统计时间。
- 单行操作统一为**详情、编辑、暂停/恢复、重试、复制、删除**；权限或能力不允许时解释原因，不以“前往 Link 管理”代替操作。
- 点击行打开右侧详情抽屉，移动端为全屏详情；数据按 Workspace 切换清理，防止旧请求覆盖新空间。

### 统一「创建转发」表单

**基本信息**：名称、TCP/UDP/both、入口监听端口（如当前实现支持自动分配可选留空）、目标地址和目标端口。

**网络路径**：普通直连、普通中继、FXP 加密中继；按照选择展示入口节点以及必要的出口节点，不暴露不可用拓扑。

**策略（折叠）**：入站/出站限速、并发数、监听作用域、支持组合下的目标集、来源信任/PROXY；全部复用现有校验，不把 FXP 不支持的字段伪装为支持。

**高级资源（有权限时展开）**：自动管理（默认）/指定已授权 Link；手动配置载体端口与 Link 维护入口仅对具备相应管理权限的用户开放。

提交后显示同一转发的操作进度：“提交成功，等待部署” → “入口/出口就绪” → “已就绪”。当目标没有探测数据时显示“目标可达性未验证”，不可把 Ready 当可达。

### 详情抽屉

分为“概览、配置、流量、诊断、历史/高级”五部分。诊断按“入口监听 → 节点间载体（若有）→ 出口 → 目标”展开；上报缺失时显示 `unknown/stale`，不编造绿色健康。**普通业务编辑仍在抽屉内完成**，高级 Link 运维可进入 `/links` 但不是前置步骤。

## 4. 后端架构与接口

### 4.1 新增统一业务协调层

建议在 `backend/src/services/` 新增 `forward-application.ts`（命名可在实现时固定），职责为：

1. 单一的业务输入校验、Workspace 权限和配额校验；
2. Path × Transport × Protocol 能力准入；
3. Native/FXP 写入分流；
4. FXP Link 选择、创建与引用编排；
5. 操作回执、幂等状态和统一状态投影；
6. 操作失败恢复及前端可解释错误码。

它只负责**协调**，不取代既有 `link-resource.ts`、FXP 编译器、ForwardRevision、租约、fencing、Agent 和原生 reconcile。一个 Forward 在任一时刻只能由一个运行时所有者写入：Link 绑定规则必须继续被原生部署路径排除。

### 4.2 接口建议（统一业务新契约，非现有 API）

```text
POST   /api/forward-operations          # 幂等创建业务转发；返回 operation_id + forward_id（如已持久化）
GET    /api/forward-operations/:id      # 查询原始操作及部署进度
GET    /api/forwards/:id                # 统一详情、传输与状态投影
PATCH  /api/forwards/:id                # 统一编辑入口，内部按归属委派
POST   /api/forwards/:id/actions        # suspend/resume/retry/delete
GET    /api/forwards/capabilities       # 按 Workspace、节点和功能开关给出可选组合
```

已有 `/api/forwards` 原生接口和 `/api/links/:id/forwards` Link 专用接口**保留兼容**，新的协调服务在服务层调用经过抽取的内部方法，避免后端 HTTP 回调自身，也避免重复实现安全检查。接口最终形状在 U0 契约测试中冻结。

统一创建请求示意：

```json
{
  "idempotency_key": "client-generated-uuid",
  "name": "日本 API",
  "path": "relay",
  "transport": "fxp_v1",
  "protocol": "tcp",
  "ingress_node_id": 12,
  "egress_node_id": 23,
  "listen_port": 30000,
  "target_host": "10.0.0.5",
  "target_port": 443,
  "transport_options": { "selection": "auto" }
}
```

用户请求成功保存但尚未确认实际部署时，应返回明确的 `accepted/pending_apply` 语义和查询位置，**不能将操作接收 202 当成运行成功**。旧客户端和新客户端可以通过版本化路径/能力门禁逐步共存。

## 5. Link 自动复用与创建规则

### 5.1 Link 资源归属

增加 Link 归属属性（具体 Prisma 字段名在迁移评审中冻结）：

- `managed_by`: `manual`（默认，覆盖所有存量 Link）或 `auto_forward`；
- `reuse_key`: 自动连接复用身份，按 Workspace、节点顺序、FXP 版本、传输/安全配置标准化生成；
- `last_unreferenced_at`: 自动连接零引用后的回收候选时间；
- 不对存量 Link 自动打上 `auto_forward`，也不在未授权情况下自动使用用户手动管理的 Link。

### 5.2 复用判定

依次校验：同 Workspace；同固定入口/出口角色与连接身份；加密传输及安全策略兼容；资源未退役且不在维护围栏中；节点角色、地址、实际 Agent 能力和新鲜事实满足要求；引用上限与端口使用安全。仅 `auto_forward` Link 默认参与自动复用，手动 Link 只有用户明确指定且具备使用权限才可关联。

**零引用 Link 的入口可能处于 passive/ready=false，这是正常的，不能简单因其未 Ready 就判定不可复用。** 同时，不得把正在失败回收或事实未知的 Link 当作安全可用资源。

### 5.3 并发与安全创建

- 统一事务内登记幂等请求、校验完整 Workspace/策略、选择并锁定复用候选，或在唯一复用键保护下新建 Link 及首条 ForwardRevision。
- 自动分配载体端口须复用现有 NodePortLease/占用守卫机制，并处理竞争、失败补偿；不能仅用数据库 `MAX(port)+1` 或随机尝试后忽略 Agent 事实。
- 将实际双端部署放在数据库事务**之外**，经现有 Worker/Link 部署机制执行；记录作业状态以供查询与恢复。
- 同一幂等键、同一 Workspace/用户、同一规范化请求返回同一结果；同键不同请求返回明确冲突；网络超时通过 `GET operation` 确认，不重复写业务。
- 新 Link 成功而部署失败时保留可追踪的业务规则与错误状态，由受控 reconcile/retry 修复，**不得悄悄改用普通明文 Forward**。

## 6. 统一 Forward 生命周期

| 操作 | 普通 Forward | FXP Forward | 外部行为 |
| --- | --- | --- | --- |
| 创建 | 原生创建/修订 | 自动找/建 Link 后创建绑定 | 同一个表单与操作回执 |
| 编辑 | 既有 Forward 修订 | 调用 `updateLinkForward` 语义 | 同一个编辑抽屉；明确版本冲突 |
| 暂停/恢复 | 原生运行时 action | Link 托管 action + 合并部署 | 同一个控制入口 |
| 重试 | 原生 reconcile | Link deploy/reconcile | 查询同一规则的状态 |
| 删除 | 原生停止与释放 | Link 编译移除引用、部署确认、再删除业务实体 | 未停止完成不能假报删除成功 |
| 复制 | 原生草稿复制 | 复制业务字段，重新选择 Link 复用 | 不复制密钥或端口所有权 |

不可就地安全修改的字段（如 FXP 协议、监听作用域、某些节点或加密方式）应**明确阻止并提供“创建替代规则”引导**。V1 不应把跨模式修改伪装成无中断热切换；未来有 F5 迁移执行器和正式验收后再开放对应变更。

用户删除最后一条自动 Link 引用后，将 Link 置为待回收候选；只有确认无引用、运行已停止、租约与实际端口守卫可安全释放后再退役。手工创建的 Link 默认保留，暂停 Forward 仍计入引用，不因没有活跃监听就误删。

## 7. 权限与安全设计

- 业务转发 CRUD 以 `forward:read/create/update/delete` 为主；创建或使用**已授权**的 FXP 转发不应自动要求 `node:manage`。
- 新增或复用显式的 Workspace 节点资源使用授权（具体 RBAC 能力键在 U0 冻结）；系统受控服务身份只能在用户获准节点/路径范围内代建托管 Link，不能越权管理任意 Node。
- `node:manage` 仍用于手动 Link、密钥轮换、载体/节点资源维护、授权节点管理等高级操作；每次请求在服务端检查，不依赖隐藏前端按钮。
- Link 密钥、密文、runner 配置、原始目标策略不得泄漏到列表、普通详情、操作回执、前端日志或 Support Bundle。
- 前后端继续执行功能开关与新鲜 Agent 能力门禁；协议不兼容、节点不可达、失去授权、端口冲突、配额耗尽必须明确拒绝；绝不静默回退明文。

## 8. 状态模型和故障反馈

状态分维度投影：

1. `desired`: 用户期望（active / suspended / deleting）；
2. `deployment`: accepted / pending / applying / confirmed / failed / unknown；
3. `runtime`: ready / passive / stopped / stale / unknown；
4. `transport`: native / FXP，含节点间连接可用性；
5. `target_health`: healthy / unhealthy / unverified；
6. `traffic`: 累计流量、速率与最后接收时间（没数据不展示虚假零值）。

UI 主状态简化成“待部署、运行就绪、目标异常、已暂停、部署失败、状态未知”，并在详情中解释依据；目标健康与 runtime Ready 不混为一谈。超时和未知写入结果应提供“检查创建结果”和“安全重试”入口，而不是直接再次 POST。

## 9. 兼容、迁移与发布开关

- Prisma 做**增量迁移**，所有存量 Link 默认 `manual`，原有 Link/Forward 外键、历史 ID、ForwardRevision、统计检查点保持不变。
- 旧 `/links` 页面继续存在，定位为“高级加密连接管理”；普通用户侧导航可在统一流程稳定后隐藏入口，但不能删除已有访问路径/API。
- 添加独立开关，例如 `TUNEX_FORWARD_UNIFIED_UI_ENABLED`、`TUNEX_FORWARD_AUTO_LINK_ENABLED`，作为新代码的渐进准入；它们**不能覆盖**既有 `TUNEX_FXP_LINKS_ENABLED`、Agent 能力及 Workspace 策略。
- 灰度顺序：内部开发环境 → Linux 多 Agent 测试环境 → 受控 Workspace → 具备完整发布证据的默认路径。
- 回滚前端/统一入口开关不会撤销已经合法创建的 Forward；新创建操作关闭后，已有记录仍可由兼容的旧接口和现有 reconcile 管理。部署中操作不得因版本回滚失去查询与恢复入口。

## 10. 分 PR 开发拆分

| 阶段 | 工作内容 | 合并验收 |
| --- | --- | --- |
| **U0：契约与基线** | 冻结 Path/Transport 枚举、支持矩阵、权限规则、统一状态 DTO；补旧路径回归 | Native/FXP 全部存量对象能正确投影，无数据修改 |
| **U1：统一读取与操作** | 后端统一详情、编辑、启停、删除/重试分流；前端不再跳 `/links` | FXP 从 `/forwards` 完成全生命周期，后台仍仅 Link 写入 |
| **U2：资源授权与自动 Link** | 明确 node-use 授权；增加 managed_by/reuse_key、并发安全复用、自动端口选择 | 普通 Forward 用户在授权范围内无需 `node:manage` 即可创建 FXP |
| **U3：幂等的一键创建** | 统一创建契约、操作回执、持久状态、Worker 恢复 | 一次业务提交；超时/重复点击不重复创建或产生孤儿占用 |
| **U4：完整转发工作台** | 新创建表单、详情抽屉、过滤、状态、诊断、受控高级配置 | 桌面/移动端一页闭环，支持中英文与无障碍状态 |
| **U5：实网验证与发布** | 多 Agent/数据库/浏览器全流程、故障注入、跨版本升级、灰度和回滚 | 功能开关开启范围均有可复查的运行证据 |

顺序上先 U0/U1，实现“同一页面管理”；然后 U2/U3，实现“无需理解 Link 的一次创建”；最后 U4/U5 做体验统一与发布。必要的前端组件可以伴随各阶段开发，不做一次性大重写。F5 在线维护与 F6 拓扑扩展使用此统一业务契约作为后续接入基础，而不作为本轮完成条件。

## 11. 强制验收场景（Definition of Done）

- **基础**：Native DIRECT、Native RELAY、FXP 双节点分别创建、访问真实 TCP/UDP；`both` 只在对应开关和能力准入下测试及开放。
- **复用**：同 Workspace 同兼容节点对创建两条 FXP Forward，可共享受控 Link；更新 A 不断开未变的 B TCP 与固定 UDP 映射。
- **隔离**：跨 Workspace、禁用节点、不可用 Agent、旧能力上报、手动 Link 未授权、超配额均被拒绝。
- **并发**：两个相同首建请求并发、重复幂等键、同键不同请求、候选端口被其他进程占用，不产生重复资源或错误释放。
- **失败**：创建后丢响应、Link 创建后部署失败、入口成功出口失败、Agent/Worker 重启、迟到 ACK，均可追踪与安全恢复。
- **生命周期**：编辑/暂停/恢复/删除 FXP 在 `/forwards` 完成；删除最后引用后自动 Link 仅在真实运行退出、租约安全释放后回收。
- **安全**：禁用 FXP 或失去权限时绝不降级为 Native；链接密钥及私有快照不进入 UI、API 公开投影或日志。
- **观测**：确认部署不等于 Ready，Ready 不等于目标健康，统计收到不等于当前存活；缺失事实明确显示 unknown/unverified。
- **升级**：旧数据库迁移、旧原生 Forward、旧手动 Link、旧 FXP 规则完整保留；新开关关闭和版本回滚仍有受控操作路径。
- **验收证据**：候选 SHA CI、真实 Linux 多 Agent payload、MySQL/Redis、真实浏览器 API 流程、故障注入、长期计量及脱敏日志；历史 CI 绿灯不替代当前发布验证。

## 13. V2.0 原生化目标：TuneX 原生化与自主实现边界

### 13.1 定义与范围

原生化分为两层：

1. **业务原生化（U 系列）**：统一 Forward/Node/Path/Transport/Link 模型、权限、编排和 UI；前端不直接依赖 FXP 专有资源结构。
2. **运行时原生化（N 系列）**：TuneX 独立设计并实现节点间安全传输、TCP/UDP 数据通道、会话生命周期、配置热更新、流量计量及故障恢复，最终不再构建、打包、调用 ForwardX FXP 代码或可执行程序。

**硬性要求：可以研究 ForwardX 的公开功能、用户体验、模块职责、测试需求与通用工程问题；不得复制、翻译、机械改写、移植或派生其源代码。** 新原生协议不以 FXP 的帧格式、握手、密钥格式或内部 API 为实现契约。使用公开标准（如 TLS 1.3）及 Go 标准库/经审查的第三方密码学库，不自行发明密码算法。对于许可、专利、商标和既有导入组件的分发义务，在发布前单独审查；独立实现不能自动消除已有版本的许可义务。

当前源码事实：`third_party/forwardx/forwardx-fxp` 是导入并修改的执行组件，`agent/internal/linkrunner` 管理该外部进程、端口、租约、配置热更新与恢复。`backend/src/integrations/forwardx/` 包含支持矩阵和 FXP 编译边界。**这些现有路径不是新原生代码的复制模板，也不能在替换完成前直接删除。**

### 13.2 目标架构

```text
TuneX Web / API
      │  Forward 业务契约（与运行时解耦）
      ▼
Forward Application / Controller
      │  Path × Transport × Protocol 能力选择
      ├── Native legacy adapter（存量直连/中继）
      ├── FXP legacy adapter（存量 Link；过渡期保留）
      └── TuneX Secure adapter（新协议；功能开关默认关闭）
                         │
                         ▼
                 TuneX Agent (Go)
                 ├── Listener / Port Guard
                 ├── TCP Stream Engine
                 ├── UDP Session Engine
                 ├── Secure Channel / Auth
                 ├── Rule Snapshot / Hot Reload
                 ├── Rate Limit / Accounting
                 └── Lease / Recovery / Observability
```

`LinkResource` 在业务语义上仍表示可复用的节点间连接资源；运行时应具有显式 `transport_kind` / `runtime_owner` 与协议版本。旧 FXP 与新 TuneX Secure **不能因为节点对相同就复用同一个物理 Link 或混用密钥/配置代次**。业务 Forward 的唯一写入所有者规则、CAS、端口守卫、租约及 Workspace 隔离继续适用。

### 13.3 原生协议设计要求（N0 冻结）

- 独立标识与协商：例如 `tunex-secure/v1`，固定协议版本、消息大小限制、功能协商、拒绝未知字段/版本；**不承诺兼容 FXP wire protocol**。
- 身份与加密：双向节点身份认证、可信密钥配置或证书体系、成熟标准加密套件、密钥轮换策略、握手失败闭锁；任何认证失败不得退化为明文。
- 授权：身份认证不等于目标访问授权。每条 Forward 必须绑定 Workspace、入口、出口、规则 ID、目标和允许的协议；出口按服务端下发的授权快照强制校验。
- TCP：双向流复制、背压、半关闭、取消与超时、连接/内存上限；未变化规则热更新时保持既有会话。
- UDP：源会话映射、回包路由、空闲过期、映射容量上限、重放防护、乱序处理；不假定 UDP 具有可靠送达语义。
- 控制面：不可变规则快照、版本/代次、digest、幂等 ACK、超时补偿、重启恢复；控制与数据通道的权限隔离。
- 资源与观测：载体端口预留、租约、故障检测、限速/并发、按 Forward 的统计、健康与流量新鲜度分离，禁止日志泄露密钥与用户负载。
- 安全设计先行：形成威胁模型、协议状态机、失败策略和独立审查清单；密码学/协议安全审查完成前不得标记为生产可用。

### 13.4 自主实现与参考边界

| 可参考的需求或标准 | 不可作为新原生实现来源 |
| --- | --- |
| ForwardX 对外展示的功能和用户工作流 | 其 Go/其他语言源文件、算法实现或配置热更新代码 |
| 常见转发系统的架构职责和测试场景 | FXP 的具体帧布局、握手过程、内部私有协议和函数结构 |
| RFC、公开密码学标准、Go 标准库 API | 对 ForwardX 代码进行重命名、逐行翻译或结构性改写 |
| 自主编写的黑盒需求测试与性能目标 | 将 `forwardx-fxp` 包装后声称为 TuneX 原生运行时 |

研发留痕：新协议设计文档、来源记录、独立实现 PR、测试用例来源与依赖清单。旧 FXP 可在过渡期作为**黑盒兼容性/行为对照**，但新原生协议的代码、测试实现和安全假设应独立构建；不得依赖阅读其内部实现来照搬细节。需要兼容旧协议时另立兼容项目并进行许可审查。

## 14. N 系列工作包与依赖

| 阶段 | 交付内容 | 验收门槛 |
| --- | --- | --- |
| **N0：独立协议与依赖盘点** | 协议规范、威胁模型、模块 API、能力矩阵、旧 FXP 构建/运行依赖清单、性能基线 | 独立评审通过；新协议与 FXP 不共享 wire 契约 |
| **N1：原生 TCP/UDP 引擎** | Agent 连接/会话、监听、限额、背压、关闭、UDP 映射和资源清理 | 双节点实网 TCP/UDP、并发、超时、压力和泄漏测试 |
| **N2：TuneX Secure v1** | 双向认证、加密通道、密钥管理、重放防护、授权绑定、协议错误处理 | 安全测试、负面测试、外部/独立审查；默认关闭 |
| **N3：Link 与业务接入** | 新 Transport Adapter、自动 Link 复用、规则级更新、状态投影 | 同一 Link 多规则，变更 A 不破坏 B，不能跨运行时误复用 |
| **N4：生产运行能力** | 计量、限速、故障恢复、代次、端口保护、升级、诊断、平台支持矩阵 | 重启/断网/迟到 ACK/部分部署/长期负载实测 |
| **N5：灰度迁移与清理** | 新旧运行时并行、显式迁移、回滚、移除构建/运行依赖、许可证清单核查 | 现网迁移可控；新安装不含 FXP 依赖；完整发布证据 |

### 14.1 推荐实施顺序

```text
U0 统一业务契约 ──→ U1 统一管理操作 ──→ U2/U3 自动 Link/幂等创建 ──→ U4/U5 页面与业务验收
       │                                                           │
       └──→ N0 协议与威胁模型 ──→ N1 TCP/UDP ──→ N2 Secure ──→ N3 接入 ──→ N4 验收 ──→ N5 迁移
```

N0 可与 U1 并行，但 N3 必须依赖 U0 的稳定契约和 U2/U3 的资源所有权/幂等约束。新协议实现与现有 FXP 功能不得互相覆盖，任何新传输组合必须有独立的能力门禁和功能开关（建议 `TUNEX_SECURE_V1_ENABLED`，名称在 N0 冻结）。在 N2/N4 通过安全和实网验证前，不得默认开放新协议。

### 14.2 迁移与回滚

1. **不做原地协议替换**：存量 FXP Link/Forward 保留原运行时身份；新协议新建 Link 资源或使用显式迁移工作流。
2. **并行验证**：先为新规则启用 TuneX Secure，再在维护窗口内迁移旧规则；入口端口切换须经端口所有权协调，不能两个运行时同时监听同一地址/端口。
3. **明确中断边界**：FXP 与 TuneX Secure 协议不互通，既有 TCP 会话和 UDP 映射不承诺无损迁移；采用经验证的停机切换或预备/切换/回收流程。
4. **可恢复**：迁移记录包含源/目标运行时、期望配置版本、状态、切换结果及补偿动作；失败时按已验证的旧配置恢复，绝不隐式明文降级。
5. **删除依赖门槛**：只有旧 FXP 引用清零、升级/回滚路径明确、构建及容器镜像验证通过、历史许可和来源信息妥善保存后，才移除 `third_party/forwardx` 及对应 runner/编译路径。

## 15. 原 V1.1 验收条件（V2.0 继续强化）

- **业务闭环**：用户只需 `/forwards` 即可创建、编辑、暂停、恢复、诊断和删除直连/中继/加密转发；Link 默认由系统安全管理。
- **独立实现**：新安装和运行 TuneX Secure 不需要 ForwardX 源码、二进制或动态运行依赖；构建清单与镜像扫描可复核。
- **安全闭环**：双向认证、逐规则授权、密钥安全、重放防护、隔离、故障闭锁通过审查；无静默明文降级。

- **来源闭环**：新代码为独立实现；保留第三方依赖、既有导入代码和历史发行版本的必要许可证与来源记录。

**版本结论：V1.1 = U 系列统一 Forward 业务 + N 系列 TuneX 自主原生运行时。产品对外默认能力以实际通过发布门槛的组合为准，不以路线图或枚举名称代替已实现状态。**

## 16. V2.0 破坏性重构总纲（覆盖前文冲突条款）

### 16.1 决策优先级

1. **最终目标优先于历史兼容**：以单一 TuneX 原生 Forward 控制面、Link 资源模型、Go Agent 数据面为目标；可以删除旧接口、旧表、旧环境变量及旧测试夹具。
2. **自主实现优先于换名包装**：ForwardX 只可参考功能、可观察行为及公开标准；禁止复制、翻译、改写或搬运其实现。新的协议 `tunex-secure/v1` 独立设计，默认不与 FXP 互通。
3. **唯一权威写入源**：业务期望状态由 Controller 管理；Agent 只执行版本化快照。一个 Forward 不得同时被 legacy tunnel 和新 Link runtime 写入。
4. **逐项替换、即时删除**：替换模块达到门槛后，立即删除其旧入口和死代码，不建设永久兼容适配器。
5. **安全与数据底线**：即使允许重置开发数据库，也必须事先确认环境、备份与回滚点；禁止误删用户数据、明文降级、端口遗留及泄漏密钥。

### 16.2 V2.0 最终非目标

不承诺旧 FXP 配置的在线无损迁移、不承诺与 ForwardX 节点互通、不承诺旧 API/Schema 的向后兼容、不把未通过实网验收的多跳、WireGuard、GOST 或 Windows 组合纳入首发范围。若开发环境无真实业务数据，可以选择一次性 Schema 重建，但必须明确执行对象并记录迁移方式。

## 20. 原生安全传输的硬性技术约束

- 使用经过审查的标准密码学库与成熟原语，不自行发明加密算法。协议文档必须明确双向身份、密钥派生、nonce/序列、重放窗口、会话隔离、密钥轮换、版本协商、降级拒绝、资源上限与错误行为。
- TCP 必须处理半关闭、双向背压、超时、取消和长连接；UDP 必须处理映射生命周期、乱序、超时、响应关联、上限和清理。
- 配置必须按版本/代次确认；Agent 不接受过期命令，异常回滚不得复活已删除监听。新旧运行时不可同时持有同一端口。
- 加密通道不可用时直接失败，不允许自动切换到明文 RELAY。Agent 上报能力必须来自实际可运行的模块，而非仅有枚举值。
- 热更新需明确哪些字段可无损更新；载体端点、密钥或协议变更可以中断连接，必须显示风险，不能虚假承诺零中断。
- 不将密钥、完整连接配置、敏感目标、可执行命令输出直接暴露到前端日志或错误信息。

## 23. V2.0 最终协议决议：TST/1 取代 FXP（2026-10-11）

**规范性决策**：TuneX 的正式加密节点间传输仅采用自有 **TuneX Secure Transport (TST)** 协议，首个版本为 `tst/1`。这是新设计的协议与 Go 实现，不是 ForwardX FXP 的更名、复制、翻译、移植或改写。ForwardX 仅可用于需求、公开行为与测试场景的功能性比较，不得作为 TST 代码或数据帧设计的实现来源。最终发布产物、构建链和运行路径不包含 `forwardx-fxp`、FXP wire format、FXP 配置解释器或 FXP 协议兼容层。

**协议与密码学的边界**：自研的是业务帧、多路复用、规则授权、UDP 数据报映射、连接池、流控、生命周期和观测契约；加密算法、TLS 握手、随机数生成和密钥派生使用经过验证的 Go TLS 1.3 实现及成熟密码学库，不自创密码算法。`tst/1` 必须有独立的规范、威胁模型、互操作测试向量及协议版本号。

**最终唯一执行路径**：`/forwards` → TuneX Forward Controller → TuneX Agent → TuneX Native Runtime / TST Secure Transport。Link 继续是 TuneX 自有的可复用内部资源，不等同于 FXP；旧 FXP Link 数据允许在开发阶段进行破坏性迁移或明确废弃，不保证旧密钥、会话或数据帧与 TST 兼容。

### 23.1 TST/1 的首版边界

- 支持固定两个经授权节点的入口—出口加密连接；业务协议 TCP、UDP、both 按能力协商与测试结果开放。
- TCP：多路业务流、双向转发、半关闭、RST/取消、背压、流/连接级窗口及公平调度；不允许无限缓冲。
- UDP：有界数据报、关联 ID、会话映射、空闲超时、资源配额、响应路由；明确 TCP 承载时的队头阻塞问题，不声称等同于 QUIC。
- Link：多条 Forward 安全复用同一认证连接；退出节点必须基于已部署且有版本约束的规则授权目标地址，不能仅凭连接认证放行任意目标。
- 动态更新：规则级添加、修改、删除、暂停、恢复；不受影响的规则和连接尽量保持，明确不支持无损迁移的情形。
- 默认拒绝：协议版本不兼容、身份/Workspace/Link 不匹配、授权缺失、证书失效、配置版本过旧时 fail closed；绝不自动降级至明文。
- 第一版不承诺 FXP 互通、跨 Workspace Link、多跳安全链路、无损跨协议会话迁移或 QUIC 传输。

## 24. TST/1 协议规范与安全要求（T0 必须冻结）

### 24.1 身份与加密

1. 以 Go TLS 1.3 为加密基础，双方采用 mTLS 证书认证；证书签发、轮换、吊销/失效策略、节点绑定和私钥权限必须明确。
2. 验证链路双方节点身份、Workspace、Link 身份、角色和控制面授权，防止跨租户连接复用、未知节点加入和凭证误用。
3. 明确 TLS 应用协议协商标识（ALPN）、协议版本协商与不支持版本的拒绝行为；不得退回到 TLS 1.2 或明文。
4. 优先使用 Go TLS 1.3 支持的现代 AEAD 密码套件；不得在 TLS 上再设计未经审计的自定义加密层。
5. 规定证书和私钥存储、热轮换、失效处理、时间偏差和审计日志的脱敏边界；禁止日志输出密钥、原始握手材料和敏感目标凭据。

### 24.2 帧格式（设计草案，非最终二进制规范）

逻辑字段包括 `type`、`flags`、`stream_id/association_id`、`length`、`payload`。具体字节宽度、编码、大小上限、解析顺序、未知帧处理、版本和扩展机制在 T0 冻结；任何解码前都须有严格长度与内存上限。

消息类型至少考虑：`OPEN`、`OPEN_ACK`、`DATA`、`FIN`、`RESET`、`DATAGRAM`、`WINDOW_UPDATE`、`PING`、`PONG`、`GOAWAY`、`ERROR`。控制消息与业务流必须分离，防止数据流饥饿导致租约和心跳失效。

### 24.3 状态机与运行时

- 明确连接、业务流和 UDP association 的状态机、合法迁移、超时、错误码和重复消息处理。
- 定义唯一流 ID 分配、双向关闭、流控窗口更新、取消语义和错误隔离；一个规则失败不得无条件重启共享 Link。
- 规则级限速、并发和流量统计应按 Forward ID 归属，计数需要可恢复与可去重的身份及确认机制；不宣称未经验证的精确计费。
- 版本化配置、generation fence、租约、端口占用和原子应用/回滚必须与 Controller/Agent 契约一致；不接受过期配置复活。
- 明确负载与攻击面限制：最大连接数、流数、帧长度、UDP association 数、缓冲内存、握手频率和认证失败速率。

### 24.4 独立验证

必须有威胁模型、协议解析 fuzz、认证/授权负面测试、乱序/重复/截断帧测试、网络分区/断线/重连测试、配置热更新和回滚测试；双节点真实网络中验证 TCP、UDP、both、规则复用、端口冲突、流量统计和资源耗尽保护。安全审查未通过不得将 TST 标记为正式可用。

## 26. 破坏性替换与彻底清理清单

- **Agent**：替换 `agent/internal/linkrunner` 对外部 `forwardx-fxp` 进程的依赖；保留经验证可复用的 TuneX 自有端口租约、generation、状态和配置协调能力；新数据面在 Agent 内原生运行。
- **第三方源码**：最终删除 `third_party/forwardx` 及其编译产物、打包步骤、下载脚本和镜像依赖；保留法律要求的历史来源/许可与修改记录。
- **后端**：将 `backend/src/integrations/forwardx` 下真正通用的业务契约重构到 TuneX 自有模块；删除 FXP 专属 compiler/adapter、接口和兼容分支；数据库模型、字段与枚举同步收敛。
- **前端**：统一 `/forwards` 创建与生命周期管理；`/links` 仅保留必要的高级内部资源维护；不出现 FXP 专属创建向导和跳转。
- **配置与部署**：移除 `TUNEX_FXP_BINARY`、`TUNEX_FXP_LINKS_ENABLED` 等废弃开关及所有旧 FXP CLI 参数，替换为明确的 TST 功能门禁与 Agent 能力声明。
- **测试/文档/CI**：删除以 FXP 实现为必需依赖的测试夹具和构建作业，使用 TST 独立测试向量与真实双节点场景；更新 README、运行矩阵、安装器和升级说明。
- **清理方法**：每项先建立引用/依赖清单，替换并测试，再删除旧实现，最终对源码、配置、Docker、CI、Schema、文档进行全仓残留扫描；不得仅通过重命名声称原生化完成。

开发阶段允许直接废弃旧 FXP 数据和实验接口，但在执行数据库重置、销毁密钥或删除现有业务记录前必须明确记录影响范围，并保留必要的备份和回退/重建办法。**破坏兼容性不等于允许静默丢失数据或降低安全性。**

## 27. 最终 Definition of Done 与优先级声明

1. 干净环境无需 ForwardX 源码、FXP 二进制或 FXP 协议即可构建并运行 TuneX。
2. TST/1 的独立协议规范、mTLS 认证、权限绑定、TCP/UDP、多路复用、流控、限额、规则热更新、统计和故障恢复全部有自动化测试及双节点验证证据。
3. 不存在自动明文降级、跨 Workspace Link 复用、未授权目标访问、失效配置复活、秘密泄漏或残留监听。
4. `/forwards` 是普通用户唯一转发管理入口；创建、编辑、暂停、恢复、重试、删除不依赖 FXP 专属 API。
5. 源码、数据库、环境变量、容器、安装器、CI、测试和文档完成彻底清理；历史许可与来源记录按义务保留。
6. 性能指标须先测定基线、再给出可复现实测结果；不预设 TST 一定快于 FXP。

**冲突解决顺序**：本节及第 23–26 节的 TST/1 决议 > 第 16–22 节 V2.0 重构总纲 > 第 13–15 节 V1.1 原生化要求 > 第 1–12 节继承的 V1 业务设计。旧文中提及 FXP 创建、部署、特性开关和兼容适配的内容仅作为迁移前现状及业务需求来源，不再是最终技术方案。
