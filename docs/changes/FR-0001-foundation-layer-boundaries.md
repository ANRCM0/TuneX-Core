## Need And Alternatives

The earlier framework source exposed useful owner ports, but the Runtime controller
still imported SQL/concrete owners, and shared framework contracts lived under
application paths. Documentation alone cannot remove those reverse dependencies.
A wholesale Core/Runtime merger would enlarge the pure domain package and disturb
authority ownership. Instead extract the existing pure publication decisions and
move orchestration behind lower-owned ports, with explicit outer provider binding.

## Compatibility And Migration

- Keep `@tunex/core` shape and exports unchanged. The runtime kernel is separate.
- Move common definitions, not copies; old application paths re-export them, so
  ControlError identity and the same interface types are preserved.
- Production Control imports public L1 contracts. The old RuntimeController
  constructor composes RuntimeHost with original Node/Forward/ledger/Relay/authority
  owners and new state/codec adapters. No second ledger, claim or publication path.
- Keep SQL predicates/argument order, related-Node locks, boot/capability checks,
  Snapshot/report identity/sequence checks, leases, drain handling and protected
  authority-before-publication ordering. New port indirection must not open a
  connection, nested transaction or implicit business retry.
- Extract OS process observations behind the Agent platform adapter. Missing
  platform values remain absent. Sampling is not authorization or application health.
- The new flat-format v1 demo does authorized preview only and claims no old TuneX
  or external-product compatibility. It never reaches the Forward command owner.

No ADP/REST field, schema migration, driver assignment version, Probe qualification,
Journal format, high-water or existing feature default changes. There is no data
migration or state rollback procedure. Removing a source bridge later is a new
public compatibility change requiring a separate proposal and consumer inventory.
