日期：2026-10-20（Asia/Shanghai）。

## 目的与边界

D1 的目标是先取得观察池、周期任务和页面请求的负载基线，再决定是否需要按 key
合并、有界唤醒或慢消费者处理。没有基线时，不新增事件通道、调度平台或常驻
工作队列。周期对账和原事务/授权 owner 仍是正确性来源；通知不能续租、进程锁
不能替代跨实例权威。

## 待测量项

| 类别 | 需要的证据 |
| --- | --- |
| 观察池 | 节点/Forward/Probe 规模、活跃订阅数、每类请求频率、页面可见性变化 |
| 周期任务 | 任务数、执行时长分布、重叠/跳过次数、失败退避、drain 时间 |
| 页面请求 | 列表/详情/诊断/telemetry 的并发数、响应时间、响应字节、取消/超时 |
| 有界资源 | 活跃任务数、等待 key 数、等待字节、过期/取消/合并/公平性、关闭排空 |
| 稳定性 | 饱和、丢通知、重连、事务失败、清理和内存上界的持续时间与故障注入 |

## 决策规则

1. 如果基线没有明确瓶颈，记录“无需新增调度机制”的结论即可，不为 D2 强建平台。
2. 如果确有瓶颈，再评估按 key 合并、有界唤醒和慢消费者处理；必须分别定义
   待处理 key 数、字节数、活跃数、过期、取消、合并、关闭和溢出行为。
3. 事件只能加速唤醒，不能替代周期对账、撤销、执行期限或授权。
4. 任何实现都不得把同机 namespace、短时压测或历史绿灯写成独立物理主机、
   长稳或生产容量证明。
